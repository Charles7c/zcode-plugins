# Bug 诊断（先证伪，再修复）

## 目的

把「用户报告的现象」变成「可证伪的根因」，避免按报告者的猜测直接改代码。诊断是修复前的只读动作，不写产品代码。

## 何时使用（满足任一）

- 症状与代码位置不直接对应，或报告者只给了现象/截图；
- 同一 Bug 修过仍复发，或近期在同一模块反复出问题；
- 涉及认证、支付、数据迁移、并发、缓存、配置、依赖升级、版本漂移；
- 影响面跨模块/跨服务，或修复可能改变公开契约；
- 工程师第一次定位失败，或 QA 回归失败但原因不明。

简单直接的 Bug（错误信息明确、单文件单点、复现稳定）可跳过本文件，但修复报告仍要写「症状 / 根因 / 验证方式」三行。

## 诊断步骤

1. **写清事实**：症状、复现条件、环境/版本、日志/截图；已确认事实与假设分开；报告者的根因判断标为「主张」，不是结论。
2. **列候选**：给出 2–4 个**机制不同**的候选原因，覆盖不同层：输入/校验、状态/缓存、调用方/契约、配置/开关、依赖/版本、测试替身、最近改动。同一原因的三种说法不算多个候选。
3. **逐条证伪**：每个候选写 `Confirm if`（看到什么就确认）与 `Eliminate if`（看到什么就排除），并实际观察、记录结果；没有观察的候选不算排除。
4. **攻击领先假设**：主动找反例——其他调用方、默认值、开关、缓存、迁移、版本漂移、测试替身、并发时序、最近提交。
5. **查历史风险**：对将要修改的文件及其直接调用方，看近一月 `git log`：同类症状是否修过、有没有被放弃的方案、已知坑；在诊断中写「本次如何避免重犯」。
6. **定影响面**：受影响模块、调用方、契约、数据路径、爆炸半径；明确本次不修的部分。
7. **定最小验证与修复边界**：修复后跑哪条命令/用例能证明根因消失；只修根因覆盖的范围，不顺手重构。
8. **没有假设存活时**：写明证据缺口与下一步需要的输入，停下问主理人；不猜、不编根因。

## 产物

- 简单 Bug：工程师报告里的「诊断」一节（症状 / 根因 / 证据 / 验证方式）。
- 复杂 Bug：写入 `docs/bug-diagnosis.md`，并在项目简报第 7 节登记路径；修复报告引用该路径。

## 禁止

- 把报告者的修复建议当诊断；
- 用「截图显示」「应该就是」代替代码、日志、运行时证据；
- 为凑候选数量编造假设；
- 诊断阶段修改产品代码、提交或推送；
- 根因未确认就扩大改动范围。
