# 验收清单模板

## 目的

新建、修复、整改类档位在动手前必须产出 5–8 条可判定的验收项；部分工作流的单环任务至少 1–3 条。清单是工程师整改、QA 复核、审查者放行、主理人交付的共同基准。

## 模板

| # | 验收断言 | 证据来源 | 验证方式 | 当前值 | 目标值 | 结果 | 责任人 |
|---|---|---|---|---|---|---|---|
| 1 | PR 标题符合目标仓库约定 | `gh pr view --json title` | 真实运行 | 待填 | 符合仓库约定 | 未验证 | 工程师 |
| 2 | 项目声明的 lint 为 0 error | `npm run lint` 或 CI 计数 | 静态检查 | 待填 | 0 | 未验证 | QA |
| 3 | 项目声明的静态检查问题计数为 0 | 项目检查 API / CI 计数 | 真实运行 | 待填 | 0 | 未验证 | QA |
| 4 | diff 只含本次整改文件 | `gh pr diff --name-only` | 真实运行 | 待填 | ≤ 约定文件数 | 未验证 | 审查者 |
| 5 | 文档不违反仓库写作约定 | 人工对照项目文档规范 | 人工检查 | 待填 | 无违规 | 未验证 | 审查者 |
| 6 | 受影响模块测试通过 | `<测试命令>` | 测试 | 待填 | 全绿 | 未验证 | QA |
| 7 | 依赖服务不可用项已标「未验证」并给出替代方案 | 环境检查命令 / 项目文档 | 真实运行 | 待填 | 有替代方案 | 未验证 | QA |
| 8 | 文档生成/漂移校验通过 | `<文档校验命令>` | 真实运行 | 待填 | exit 0 | 未验证 | QA |
| 9 | 项目人工硬规范逐条符合（署名、注释禁词、License Header 等，按规则卡摘录） | `git diff <base>..HEAD` 逐行 + 规则卡关键词 grep 计数 | 静态检查 | 待填 | 0 违规 | 未验证 | 审查者（未派时 QA） |

结果只能填：`通过` / `未通过` / `外部阻塞` / `未验证`；「未验证」项单独列出，不得并入「通过」。验证方式为「模拟」的项只能填「未验证」或「未通过」，不得填「通过」。

## 编写规则

1. **可判定**：每条都能用命令、检查名、API 或 `文件:行号` 证明；不写「代码质量良好」这类主观项。
2. **证据具体**：写清读取方式，例如 `gh pr checks`、`gh api .../issues`、`npm test`、`git diff --stat`；`gh` 仅为示例，其他托管平台用对应 CLI/API 替换。
3. **区分检查与计数**：有计数接口的检查必须同时写「检查状态」和「问题计数」；没有计数接口的检查写「检查状态 + 证据」。
4. **覆盖三类来源**：用户明确要求、目标仓库规范条款、目标仓库声明的必过检查。改代码的任务必须含一条「人工硬规范符合」断言，条款从项目规则卡摘录并转成 grep 关键词或对照命令，不得写成「符合项目规范」这类无法判定的表述。
5. **范围变更要更新**：用户追加或修改需求时，先更新清单，再继续执行；不得把新增项塞进原清单假装原计划。
6. **项目规则与用户要求为主**：开源/自维护、发布流程等项目性质只作辅助判断；冲突时先向用户说明。
7. **环境不足不写成通过**：依赖服务/工具不可用时写「未验证」+ 替代验证方案。
8. **按需追加断言**：涉及限流/配额/权限/超限的改动，追加「拒绝路径」断言（超限或越权时返回什么、有无副作用）；涉及配置项新增/变更，追加「配置文档同步」断言；项目声明的检查在本地无对应命令时，用项目 CI/API 触发，触发不了标「外部阻塞」，不得直接跳过。
9. **计数与终态可复现**：测试数量、问题计数、检查结果必须写「命令 + 统计口径」（模块汇总还是类明细），以一次命令输出为准，禁止手算累加；CI 检查要读终态列表，CLI 退出码不作为通过证据（部分 CLI 有失败仍返回 0）。
10. **验证方式分级**：每条注明验证方式——真实运行 / 测试 / 静态检查 / 人工检查 / 模拟；「模拟」指用 mock、fixture、替身或纯静态推演替代真实运行面，结果不得填「通过」，只能填「未验证」或「未通过」并在证据来源写清模拟范围，也不得用它支撑「真实运行」结论。
11. **相邻路径（修 Bug 必填）**：至少一条断言覆盖改动模块的「相邻未受影响路径」——正常调用方或同类路径的行为与改动前一致，证据为该路径的测试或运行记录；确实没有相邻路径时写「不适用 + 理由」。

## 使用方式

- 快速模式：随需求传给工程师与 QA。
- BugFix：随 Bug 描述传给工程师与 QA；复杂/模糊 Bug 另附 `bug-diagnosis.md`，并追加「相邻未受影响路径」断言。
- 整改档：随项目规则卡传给工程师、QA、审查者。
- 标准 SOP：随 PRD/设计传给工程师、审查者、QA。
- 交付总结：逐条贴结果与证据，并写清交付落点（工作区/分支/PR/合并）。
