# 工程保障包（按需）

## 目的

工程保障包用于「审查/上线前/事故/技术债/文档」类任务，不用于日常功能开发。按任务只取 1–3 节，不要整包全跑；需要多人时优先派 1–3 个角色，不默认组 6 人队。按交付物类型取适用项；不适用项写 `N/A` + 理由（如 CLI/库无部署 Go-No-Go、无数据库无迁移）。

## 1. 代码审查

检查维度：安全（注入、越权、密钥、SSRF/XSS/CSRF）、性能（N+1、无界查询、资源泄漏）、正确性（边界、竞态、错误处理）、可维护性（分层、重复、命名、注释）。

输出：按严重度分级，每条带 `文件:行号` 与证据；结论 `PASS / PASS_WITH_MINOR / BLOCK`。

## 2. 测试策略

- 测试金字塔：单元为主，集成为关键路径，E2E 少量。
- 必测：公共 API、关键错误处理、边界条件、数据完整性、安全边界。
- 回归：先跑受影响模块，再跑项目声明的全量门禁。
- 覆盖取舍：不追求 100% 行覆盖，追求关键路径有效覆盖。

## 3. 部署前检查（Go/No-Go）

- 代码：测试通过、已审查、无待处理阻断项。
- 依赖：锁定、无已知高危漏洞、兼容性确认。
- 数据库：迁移可回滚、已备份。
- 配置：环境变量/Feature Flag 就位。
- 监控：告警、关键指标、日志级别。
- 回滚：方案明确，步骤可执行。
- 结论：Go / No-Go + 阻断项。

## 4. 事故响应

分级（P0/P1/P2/P3）→ 时间线 → 影响范围 → 根因（5 Why）→ 缓解/修复 → 行动项（负责人/截止日）→ 预防措施。

## 5. 技术债

分类：代码债、架构债、测试债、依赖债、文档债、基础设施债。优先级可用 `(影响 + 风险) × (6 - 工作量)` 粗排，输出分阶段修复计划。

## 6. 文档 / Runbook

- README：项目是什么、怎么跑、怎么贡献。
- API 文档：端点、参数、示例、错误码。
- Runbook：操作步骤、故障排查、应急预案。
- 文档必须与代码归属一致；配置项文档要核对前缀/归属类。

## 报告与 Token 规则

- 对话里只给 TL;DR + 结论卡 + 3–5 条行动项；全文落盘。
- 只读与审查可并行；写操作仍串行。
- 只取本次相关章节；不要求每次全量输出。
