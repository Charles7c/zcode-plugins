# 独立复核（verifier-critic）与证据要求

## 核心原则

**写实现的人不能自证质量。** 复核必须由未参与实现、且未看过前几轮结论的视角执行；复核者自己取真值，不采信摘要。

## 复核者的做法

1. **只看原始材料**：原始需求 + 当前 diff/代码 + 实际运行的命令输出。不看实现者的自述结论。
2. **自己跑**：能跑的命令自己跑（测试、构建、lint），不以"实现者说跑过了"为依据。
3. **逐条判定**：每条验收标准一行，结论只能是 `pass` / `fail` / `unverified`，每行必须附证据（命令 + 输出摘要，或 `文件:行号`）。
4. **方向优先**：先对照原始需求判断"做的是不是对的事"，再判断"是不是做对了"。
5. **不完整的清单不成立**：验收条数必须与定稿一致；判通过时不允许存在 `fail` 或 `unverified`。

## 禁止行为

- 用实现者的摘要代替原始需求或 diff；
- 接受"应该没问题""理论上可行"这类无证据判断；
- 把"没跑"写成"通过"；
- 复核期间改动工作区或代码。

## 结论与升级

| 情形 | 动作 |
|---|---|
| 全部 pass | 放行 |
| 有 fail / unverified | 退回实现方修复，只复核增量 |
| 两轮仍不收敛 | 如实交付，遗留项写进交付概览，禁止继续循环 |
| 需求本身歧义 | 退回产品经理澄清，不复核者自行改方向 |

## 团队落点

- **QA** 与**审查者**都按本节要求组织最终报告；
- 逐条判定用 `pass / fail / unverified`，报告整体结论用审查者的 `PASS / BLOCK` 或 QA 的路由判定；两套值不互换，也不与验收项结果混用；
- 主理人在转交下游前抽查：证据是否为真实命令输出、验收条数是否齐全。
