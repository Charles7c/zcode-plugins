# 项目规则与门禁盘点

## 目的

在任何涉及既有仓库的任务开始前，把目标仓库自己的规则和门禁变成一张可验收的「项目规则卡」。本文件不绑定任何具体工具；静态检查、质量门禁、CI 检查都只是「项目声明的检查」的实例。

## 读取清单（按优先级）

0. **项目类型**：按 `project-types.md` 识别 1–2 类，决定后续读取重点（库项目重 API 兼容，服务项目重迁移与可观测性）。
1. **仓库级指令**：`AGENTS.md`、`CLAUDE.md`、`.cursorrules`、`CONTRIBUTING.md`、`README.md`。
2. **PR、提交与交付规范**：PR 模板及粒度惯例、提交信息规范、commitlint 配置、trailer 要求、issue 关联要求、分支命名、合并方式。
3. **CI 配置**：仓库中的 CI 工作流文件与必过检查。
4. **静态检查与质量门禁**：仓库中的 lint/format/静态分析/质量门禁配置（按项目实际使用的工具读取）。
5. **构建、测试与文档入口**：构建与测试脚本、测试命令、文档生成/漂移校验脚本。
6. **运行环境与依赖服务**：Docker、testcontainers、数据库、缓存、浏览器等是否可用；不可用时记录替代验证方案。
7. **分支保护与必过检查**：`gh api repos/{owner}/{repo}/branches/{branch}/protection`（有权限时）、`gh pr checks`。
8. **依赖/API 升级**：查看对应版本的上游变更，检索可能重复的下游实现、调用点与文档；记录替换、保留或删除的依据及兼容影响。

一次批量读取，不逐个文件派子智能体。以上仅为常见位置示例，目标仓库不存在某项时跳过，不视为缺失。`gh` 命令仅为示例；其他托管平台用对应 CLI/API 替换。

## 判定规则

1. **项目规则与用户要求为主**：项目文件中的明确规则和用户明确要求是判定依据；两者冲突时先向用户说明，由用户裁决。
2. **项目性质只作辅助**：开源协作、自维护、公开 API、发布流程等性质可以帮助判断交付形态和严格程度，但不能替代明确规则或用户要求，不得想当然。
3. **检查状态与问题计数分开**：`check` 绿色只代表该检查通过；有计数接口时必须读问题数，两者都满足才算通过；没有计数接口的检查，以检查通过且证据可复核为准。
4. **区分本次与存量**：当前失败项要标明「本次改动导致」还是「存量失败」；存量失败是否纳入本次范围，由用户确认。
5. **外部不可用标外部阻塞**：网络、密钥、第三方 API、依赖服务不可用时，写清服务、错误、影响，不写成通过。
6. **基线要新鲜**：diff 范围用 `gh pr diff` / `gh pr view --json files`，或先 `git fetch origin <base>` + `git merge-base`；不得用陈旧本地 ref。
7. **人工硬规范要可判定化**：从仓库级指令摘录与本次改动类型相关的条款（改代码：署名、注释风格、License Header、命名；改文档：写作约定），逐条转成 grep 关键词或对照命令。只写「项目 AGENTS.md 全部生效」不算规则卡——成员不会因此去读全文，条款等于不存在。
8. **读取命令要对交付态稳健**：校验新建/未跟踪文件时不得用 `git grep`（对未跟踪内容必然无输出＝假通过），用文件级 `grep`，或先提交再校验。

## 交付形态盘点

在规则卡里单独记录：
- 项目是否要求 PR；是否允许直接提交或本地合并。
- 分支命名、合并方式（merge/squash/rebase）。
- 提交 trailer 键值与 issue 关联要求。
- 谁有 push/merge 权限；是否需要用户确认。

开源协作项目通常走 PR，自维护项目可能直接提交或本地合并，但这只是辅助判断；最终以项目规则和用户要求为准。

## 禁止

- 不要把某个项目的工具名写死进 SOP。
- 不要只读 README 就下结论。
- 不要用「CI 全绿」代替「项目声明的所有验收项逐条通过」。
- 不要因为项目是开源的就默认走 PR，或因是自维护的就默认直接提交。
