# 回归选型（按变更选，不按心情选）

## 目的

每次变更都跑全量，成本高、反馈慢；只跑冒烟，容易漏。回归选型的目标是：**用最小集合覆盖本次变更的风险，同时保留固定的安全网。**

## 变更映射

1. **代码变更 → 测试资产**：改动的文件/模块/路由映射到 API 用例、集成测试、E2E 用例。
2. **接口变更 → 调用方**：公开 API/契约/数据模型变更，必须覆盖所有直接调用方。
3. **UI 变更 → 路由/组件**：改动的页面/组件/菜单映射到关键路径用例。
4. **共享代码/基础设施**：公共库、鉴权、租户、缓存、序列化变更 → 按全量处理。
5. **DB Schema/迁移**：必须跑迁移 + 数据兼容（旧数据在新代码下可读/可写）。
6. **依赖升级**：跑受影响模块 + 依赖/安全扫描；若上游能力替代了本地实现，覆盖相关公开入口与调用方，并核对兼容影响和必要文档。
7. **文档/配置**：跑冒烟 + 配置校验；不改运行行为时可不跑全量。

## 套件分层

| 套件 | 内容 | 时长 | 触发 |
|---|---|---|---|
| 冒烟 | 登录 + 核心主流程 + 健康检查 | 5–10 分钟 | 每次 PR |
| 受影响回归 | 变更模块 + 直接调用方 + 相邻未受影响路径 | 15–30 分钟 | 每次 PR/合并 |
| 全量回归 | 全部 P0/P1 + 关键 E2E | 夜间 | 每日/发版前 |
| 安全基线 | 认证/权限/租户/注入 + 扫描 | 每周/发版前 | 按风险 |

## 选型规则

1. 先选 **P0 冒烟**，保证主流程可走通。
2. 再选 **变更直接影响** 的用例。
3. 再选 **相邻未受影响路径**（至少一条），证明没有误伤。
4. 共享代码/契约/迁移/租户变更 → 升到全量。
5. 无法判断影响面 → 按全量；不要用“应该没事”赌。
6. 选不出来的用例，写进「未测项」并说明原因，不静默省略。

## Flaky 处理

- 首次失败：原用例重跑一次，记录环境/时间/错误。
- 同一失败第二次：换方法（不同入口/数据/fixture/等待策略），记录尝试序号。
- 连续失败/无法稳定复现：标 `flaky`，隔离出主套件，登记 owner 与复查日期。
- 第三次相同重试禁止；不把 flaky 当通过。

## 资产维护

- 契约变更时同步更新用例与 fixture；过期用例删除或标废弃。
- 用例与需求/接口保持可追溯（ID/路径/接口）。
- 每次回归后更新通过率、失败原因、未测项、耗时。
- 新增 Bug 修复后补一条回归用例，防止复发。

## 退出标准

- P0 全通过；
- 受影响 P1 通过或有明确结论；
- 相邻路径通过；
- flaky/未测项已列出；
- 回归报告能让读者判断本次变更是否可以放行。
