# 测试简报（输入契约）

## 目的

测试简报是测试战役的单一事实源，替代“每次派发都重新讲一遍背景”。dev-team 在需要发版前测试时产出，qa-team 消费并更新；独立使用时由用户或主理人补齐。

## 模板

```markdown
# 测试简报：<项目/版本/需求>

## 1. 目标与范围
- 仓库/分支/commit：
- 变更摘要：
- 测试类型：功能 / 接口 / 回归 / UI / 安全
- 不测范围：

## 2. 验收与风险
- 验收清单：<路径或内联>
- 风险区域：认证 / 支付 / 数据迁移 / 并发 / 缓存 / 多租户 / 依赖升级
- 已知问题：

## 3. 环境与数据
- 环境 URL / 启动命令：
- 账号/角色/租户：
- 测试数据准备与清理：
- 依赖服务与限制：

## 4. 现有资产
- 测试命令 / 用例目录 / CI 检查：
- 已知 flaky：

## 5. 交付与门禁
- 交付形态：工作区 / 分支+提交 / PR / 合并
- reviewed SHA / 交付 HEAD：
- 项目门禁 / 必过检查：
- 已审范围 / 未审变更：

## 6. 交付要求
- 报告路径：
- 退出标准：
- 修复 owner / 裁决人：

## 7. 交接判定口径（dev→qa 交接时必填，缺一先问）
- 计数口径：每轮用例总数 / 允许新增的测试资产数 / 失败分类口径（源码 Bug vs 测试 Bug）；不得出现「每轮 28/28」与「允许新增用例」并存而不给总数
- 环境写权限：授权的 project / 端口 / 明确禁止触碰的实例，以及全部写操作清单与恢复方式；未授权不得执行写接口
- 探针阈值：残留/稳定性探针的迭代次数、时长、判定口径（如「3×150 次，一次异常即失败」）
- 需求口径来源：验收清单之外的契约文档（如安全设计文档）是否算需求口径，由谁确认
- 部分验证接受口径：异步线程等无稳定判定点的验证，是否接受降层结案、报告能否给「部分验证」
- 门禁凭据与链接：CI run 链接、静态分析项目 key、所需凭据的获取方式（只写获取方式，不写凭据值）
```

## 规则

1. **单一事实源**：成员不各自维护一份简报；有不同意见写进报告，由主理人更新。
2. **缺失先问**：repo/commit、环境、范围、验收清单、风险区域缺一，先问用户，不猜。
3. **不写敏感信息**：密码、token、验证码不进简报；只写账号标识与获取方式。
4. **更新而非重写**：每轮测试后更新状态、未测项、缺陷与残余风险。
5. **不替代用例/报告**：简报只做索引与决策记录，详细内容留在 `test-design.md` / `test-report.md`。
6. **与 dev 对齐**：dev-team 侧字段见 software-team 的 `project-brief.md` 第 10 节；字段以 dev 侧 `project-brief.md` 第 10 节为来源，测试口径的细节补在本简报。**两边冲突时由双方主理人裁决，裁决后由各自主理人回写本方简报**；测试成员只写报告，不直接改 dev 侧简报或产品代码。
