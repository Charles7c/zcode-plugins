# 测试用例设计（最小充分集）

## 目的

用最少的用例证明最多的风险。用例不是越多越好；每条都要能回答“它验证哪个行为、删掉会漏什么风险”。

## 预期来源（硬规则）

- 预期只来自需求侧：需求正文、验收标准、产品约定、真实用户场景、接口契约。
- **代码不定义“应该是什么”**：代码/注释/提交说明只解释“为什么”，不能单独作为预期依据。
- 需求未覆盖的行为，写成「观察项」，不判通过/失败；只有需求明确要求时才写硬预期。
- 需求未明确的文案/交互细节，不做逐字断言；记录实际值供人判断。
- 不编造 SLA、并发量、性能指标；没有依据就写“未定义”。

## 最小充分集与预算

1. **单点小改**（一条提示、一个按钮、一处样式）：1–2 条。
2. **需求明确 N 个验证点**：≤ N + 1 条；同入口、同角色、同状态、同风险的合并。
3. **超出预算**：每条必须引用需求/验收标准的原句；写不出依据就不生成。
4. **枚举式需求**（顿号/斜杠/编号列出的能力项）：逐项对账；每项要么有用例，要么在「不测/待确认」写明原因。
5. **验收标准逐条对账**：每条至少被一条用例覆盖，或写明缺什么证据。

## 用例来源

- 需求/验收标准；
- 接口契约（OpenAPI/路由/错误码）；
- 风险矩阵（认证、权限、租户、数据、并发、迁移）；
- 历史 Bug/回归问题；
- 现有测试缺口（覆盖对账）。

## 设计方法

| 方法 | 适用 |
|---|---|
| 等价类 | 输入域、状态、角色 |
| 边界值 | 长度、数值、时间、分页、文件大小 |
| 判定表 | 多条件组合（角色 × 状态 × 权限） |
| 状态迁移 | 订单/任务/审批/租户生命周期 |
| 错误猜测 | 历史 Bug、异常路径、空值/重复/并发 |
| 成对组合 | 多参数但不想全排列 |

## 用例字段

| 字段 | 要求 |
|---|---|
| ID | C-001 递增 |
| 优先级 | P0/P1/P2 |
| 类型 | 主流程/分支/异常/权限/数据/兼容/回归 |
| 前置 | 账号、角色、租户、数据、环境 |
| 步骤 | 一个动作一步，写清入口 |
| 预期 | 可观察结果 + 失败判定 |
| 数据 | 引用数据准备编号 |
| 执行面 | API / UI / CLI / 集成 |

## 观察项与正式用例

- **正式用例**：需求明确要求，能判通过/失败。
- **观察项**：需求未覆盖、实现行为不确定、极端场景；只记录实际行为，不判失败、不建 Bug。
- **冲突疑点**：实现疑似违背需求；预期按需求写，并标注「实现疑似不符，重点验证」。

## 例子抽象

需求/评论里的线上例子（组织名、账号、数据、截图）只是现象说明，不是测试对象：

- 提炼触发条件（什么操作、什么状态、什么配置、什么数据形态）；
- 在测试环境用自建数据构造等价场景；
- 用例步骤不写“到线上验证/找某个组织/用线上数据”。

## 数据准备

- 列出用例真正需要的数据；公共账号/入口只写一次。
- 用语义化名称；不硬编码示例对象。
- 写清创建、复用、清理；优先独立租户/前缀。
- 不要求或交付密码、token、验证码。

## 执行面选择

| 能证明的方式 | 选择 |
|---|---|
| 接口能证明 | API，不用 UI |
| 需要 DB/事务/迁移 | 集成测试 |
| 用户可见交互/路由/权限菜单 | UI E2E |
| 纯命令行 | CLI 输出/退出码 |
| 纯文档/配置 | 静态检查/人工核对 |

## 自检

- 每条用例只有一个主类型、引用数据编号、步骤独有、预期可验证；
- 至少一条 P0 主流程冒烟（无用户可见行为时说明原因）；
- 验收标准逐条有落点；
- 没有把观察项写成正式用例；
- 没有为凑数量拆分。
